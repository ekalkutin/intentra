# Intentra — План работ

> Версия: 0.1
> Статус: согласован
> Основание: `PRD.md` v0.1
> Горизонт планирования: до первого пилота и публичной презентации

Документ отвечает на два вопроса: **что входит в MVP** и **в каком порядке это делается**.
Он намеренно высокоуровневый: не содержит решений по реализации, схемам данных и
инфраструктуре. Каждое такое решение принимается внутри своего среза.

---

## 1. Что должен доказать MVP

MVP одновременно обслуживает две цели:

1. **Пилот** — реальная команда может провести на Intentra настоящий проект.
2. **Презентация** — сценарий показывается вживую и звучит убедительно.

Из этого следует главное ограничение плана: **каждый срез заканчивается чем-то, что
можно показать**. Фаз вида «сначала весь бэкенд, потом весь фронт» нет.

Демонстрируемый сценарий MVP целиком:

> Создал организацию и проект → загрузил исходные материалы → провёл AI-интервью →
> получил реестр claims, допущений и открытых вопросов → сгенерировал и утвердил PRD,
> глоссарий, доменную модель и ADR → получил спецификации → изменил требование и увидел,
> что затронуто → собрал Handoff Package → подключил Claude Code по MCP, агент прочитал
> контекст проекта и вернул предложение изменить требование → нажал Approve.

## 2. Границы MVP

### 2.1. Входит

| Область | Глубина в MVP |
| --- | --- |
| Identity | email + password, сессия; провайдер за портом под будущий Keycloak/Zitadel |
| Tenancy | Organization → Workspace → Project — вся иерархия сразу |
| Доступ | Сокращённый набор ролей поверх настоящего permission-слоя |
| Артефакты | Статусы, immutable-версии, история, ручное редактирование, review/approval |
| Knowledge Intake | Загрузка документов/ссылок/текста как `Source` → `Evidence` с provenance |
| Discovery | Один playbook (greenfield), claims, assumptions, open questions, readiness |
| Product Definition | PRD, Glossary, Domain model, ADR, Specification |
| Агенты | Три роли — Discovery, Spec Writer, Architect — как конфигурации одного рантайма |
| Traceability | TraceLink, граф в обе стороны, impact analysis при изменении, review queue, baselines |
| Handoff | Handoff Package из slice'а спецификации, Markdown/JSON, version-pinned |
| MCP Server | Чтение контекста/версий/handoff/traceability/impact + поиск + write-предложения |
| Governance | Базовый audit log, включая `McpAccessEvent` |
| UI | React + Vite, структурированные формы + сгенерированный документ для чтения |

### 2.2. Не входит

| Область | Почему отложено | Приоритет после MVP |
| --- | --- | --- |
| Delivery Management — epic/story/task, Kanban | Цепочка MVP обрывается на спецификации | **Высокий (P1)** |
| Brownfield — импорт репозиториев, as-is system map | Самостоятельный подпродукт, конкурирует с code-intelligence-инструментами | **Высокий (P2)** |
| Комментарии, mentions, threads | Совместный процесс в MVP не проверяется | Средний (P3) |
| Инвайты, email-уведомления | Нет почтовой инфраструктуры и она нигде больше не нужна | Средний (P3) |
| Полный набор из 12 ролей, кастомные роли | Добавляются данными поверх permission-слоя | Средний (P3) |
| Экспорт в Jira/Linear, двусторонний sync | Выбор трекера не сделан (PRD §17 п.3) | Низкий (P4) |
| Outbound/inbound webhooks, Public API | Нет потребителя до пилота | Низкий (P4) |
| OAuth-подключение MCP-клиентов | Токенов достаточно для того же эффекта | Низкий (P4) |
| MCP write как полноправное авторство | Требует RBAC для non-human principals | Средний (P5) |
| Custom agents, tools/skills, credentials vault, budgets | Не проверено, какая автономность приемлема (PRD §17 п.7) | Средний (P5) |
| Учёт стоимости и токенов LLM | Сознательно принят риск неконтролируемого расхода на MVP | Средний (P5) |
| Coverage gaps, release-readiness gates | Считать не на чем без story/test-слоя | Вместе с P1 |
| Voice-интервью, real-time collaborative editing | Отложено самим PRD §13.2 | Низкий |
| Локализация ru/en интерфейса | Тексты не хардкодятся, i18n подключается позже | Низкий |
| Биллинг, планы, лимиты, Commercial Entitlements | Нет платящих пользователей | Низкий |
| Наблюдаемость: метрики, трейсы, алерты | Один пользователь, один процесс | Низкий |
| Полный экспорт проекта, PDF | Handoff Package покрывает потребность MVP | Низкий |
| WCAG 2.2 AA как формальная цель | В MVP — только гигиена вёрстки и клавиатуры | Низкий |
| SSO/SCIM, MFA, BYOK, data residency, DR | Enterprise-требования, до пилота не проверяются | Низкий |

### 2.3. Что сделано вне плана

**Деплой и окружения** — вне этого плана, делается владельцем проекта самостоятельно.
План не закладывает работ по CI/CD, инфраструктуре и хостингу.

## 3. Порядок работ

Срезы идут последовательно: каждый опирается на предыдущий. Оценки относительные
(S — дни, M — 1–2 недели, L — больше двух недель) при работе в одиночку с агентами.

### S0 — Каркас приложения · S

Скелет модульного монолита поверх существующего Nx-монорепо, каркас SPA,
аутентификация email/password, сессия.

**Показываем:** вход в систему и пустой экран с именем пользователя.
**Контексты:** Identity & Account Management.

---

### S1 — Tenancy и доступ · M

Organization, Workspace, Project, Membership. Роли поверх permission-слоя.
Переключение контекста в UI. Архивирование вместо удаления. Настройки проекта.
Audit-события пишутся с первого дня — их дописывание задним числом означает
переписывание всех обработчиков.

**Показываем:** создание организации, workspace и проекта, приглашение отсутствует —
участники заводятся администратором организации.
**Контексты:** Organization & Access Control, Project & Portfolio Management,
Governance & Compliance (минимально).

> Это тот «старт работы в Intentra», который назван обязательным для MVP.
> Все последующие срезы обязаны проверять доступ только через permission-слой.

---

### S2 — Артефакты, версии и approval · M

Общая механика для всех типов артефактов: статусы `draft → in_review → approved →
superseded/archived`, immutable-версия при утверждении, история, авторство
(человек или агент), ручное редактирование карточек, review/approve.
Документный режим просмотра появляется здесь же — без него артефакт выглядит как админка.

**Показываем:** создал артефакт руками, отправил на review, утвердил, посмотрел историю версий.
**Контексты:** Product Definition (ядро артефактов), Governance & Compliance.

> Модель авторства с самого начала оперирует принципалом «человек **или** агент»,
> а не флагом. Иначе будущий полноправный агент-автор (P5) потребует миграции смысла.

---

### S3 — Источники и evidence · S

`Source` (загруженный документ, ссылка, введённый текст) → `Evidence` с provenance,
временем импорта, классификацией и ссылкой на конкретную ревизию источника.

**Показываем:** загрузил материалы в проект, видишь список источников и извлечённых фрагментов.
**Контексты:** Knowledge Intake & Evidence.

> Модель источника проектируется так, чтобы brownfield-импорт (P2) добавлялся
> как ещё один тип `Source`, а не как параллельная подсистема.

---

### S4 — Discovery-интервью · L

Минимальный Agent Runtime: `AgentProfile`, `AgentRun`, состояния
`queued → running → awaiting_approval → completed/failed/cancelled`, execution log
со ссылками на версии контекста. Поверх него — роль Discovery: план интервью,
чат, извлечение `Claim` с ссылкой на evidence, `Assumption`, `Open Question`,
простой детект противоречий, readiness score.

**Показываем:** «вау»-сценарий целиком до реестра знаний — описал идею, ответил на
вопросы, получил структурированную картину с явными пробелами.
**Контексты:** Agent Runtime, Product Definition (Discovery subdomain).

---

### S5 — PRD, доменная модель и ADR · L

Роли Spec Writer и Architect как конфигурации того же рантайма. Генерация черновиков:
PRD, Glossary, Domain model, ADR proposals, Specification. Редактирование и утверждение
через механику S2. ADR предлагается только при реальном trade-off.

**Показываем:** от реестра знаний до утверждённого PRD, глоссария, доменной модели,
минимум одной ADR и спецификаций.
**Контексты:** Product Definition (Requirements, Domain Design, Architecture Decisions,
Specification Engineering).

> К концу S5 выполнены пункты 1–4 критериев готовности пилота (PRD §18).

---

### S6 — Traceability и impact analysis · M

`TraceLink` заводится раньше — связи создаются уже в S4/S5, по мере появления объектов.
Этот срез добавляет вычисления и представление: граф в обе стороны с фильтрами,
`Baseline`, расчёт downstream-влияния при изменении утверждённого объекта,
review queue «требует вашего внимания» (без дедлайнов и эскалаций).

**Показываем:** изменил бизнес-правило — система показала затронутые требования,
спецификации и ADR, они попали в очередь на ревью.
**Контексты:** Traceability & Change Intelligence.

> Это пункты 6–7 критериев готовности пилота и ключевой момент презентации:
> здесь продукт перестаёт быть генератором документов.

---

### S7 — Handoff Package · S

Сборка пакета из slice'а спецификации: связанные требования, бизнес-правила, ADR,
контракты, acceptance criteria, ограничения. Фиксация versioned baseline.
Выгрузка в Markdown и JSON.

**Показываем:** выбрал кусок спецификации, получил готовый пакет контекста для исполнителя.
**Контексты:** Delivery Verification (минимально), Traceability & Change Intelligence.

> В MVP handoff собирается от спецификации, а не от story. Когда появится
> Delivery Management (P1), story становится ещё одной точкой сборки того же пакета.

---

### S8 — MCP Server · L

`McpClientGrant` с явным списком scopes (список, не булев флаг read-only),
project-scoped токены, policy-проверка до выполнения любого запроса,
`McpAccessEvent` на каждый запрос.

**Чтение:** `project context`, `artifact version`, `handoff package`,
`search_project_knowledge`, `get_traceability`, `get_change_impact`.
Ответы возвращают canonical IDs и pinned-версии.

**Запись (только предложения):** `raise_open_question`, `propose_requirement`,
`propose_spec_change`, `propose_adr`, submit implementation evidence.
Результат всегда попадает в статус `proposed`/`draft` и в тот же review queue из S6.
Агент никогда не переводит объект в `approved`.

**Показываем:** подключил Claude Code к проекту, агент прочитал контекст, вернул
предложение изменить требование, человек утвердил его в UI.
**Контексты:** Integration Hub (MCP Gateway).

> Доступ к одному проекту не даёт доступа к соседнему. Секреты, скрытые заметки и
> restricted evidence не выдаются никогда.
> Чтение можно выпустить отдельно, сразу после S5, если нужна ранняя демонстрация —
> запись без review queue из S6 смысла не имеет.

---

### S9 — Полировка под демонстрацию · S

Документный режим просмотра, тексты, подготовленный демо-проект, прогон сценария
целиком, устранение узких мест UX.

**Показываем:** весь сценарий из раздела 1 без остановок.

---

## 4. После MVP

Порядок отражает договорённости, а не оценку сложности.

| Приоритет | Блок | Содержание |
| --- | --- | --- |
| **P1** | Delivery Management | Initiative/Epic/Story/Task, acceptance criteria, DoD, edge cases, зависимости, Kanban внутри Intentra, handoff от story, coverage gaps и release readiness |
| **P2** | Brownfield / System Intelligence | Read-only импорт GitHub/GitLab, immutable repository snapshot, citations-based as-is system map, human-reviewed baseline, `as-is → to-be → gap`, incremental sync, secret scanning и path policy |
| **P3** | Collaboration и рост команды | Комментарии, mentions, threads, инвайты, email-уведомления, подписки, полный набор ролей и кастомные роли |
| **P4** | Integration Hub | Outbound/inbound webhooks, Public API, экспорт в один трекер (Jira **или** Linear после customer discovery), OAuth для MCP-клиентов |
| **P5** | Agent platform | Custom agents, tools/skills, credentials vault, budgets, guardrails, учёт стоимости и токенов, MCP-запись как полноправное авторство |
| **P6** | Зрелость продукта | Outcome Intelligence, Commercial Entitlements, локализация, наблюдаемость, WCAG 2.2 AA, SSO/SCIM, BYOK, data residency, DR |

## 5. Решения, на которых держится план

Изменение любого из них переписывает план, а не сдвигает его.

1. **MVP обслуживает и пилот, и презентацию.** UI обязателен; сценарий должен
   проходиться целиком без оговорок.
2. **Только greenfield.** Brownfield сохраняет высокий приоритет, но вне MVP.
3. **Цепочка обрывается на спецификации.** Handoff собирается от спецификации, не от story.
4. **Один playbook, три агентные роли** как конфигурации одного рантайма.
5. **Impact analysis — в MVP.** Без него продукт читается как вики.
6. **MCP пишет, но только предложения.** Полноправное авторство агента — цель,
   поэтому принципал и permissions с первого дня едины для человека и агента.
7. **Границы контекстов из PRD §9 не склеиваются ради MVP.** Глубина каждого
   контекста ограничивается, ownership — нет.
8. **Всё, что касается доверия к данным** (версии, audit, baselines, provenance),
   входит в MVP, потому что достраивается только переписыванием. Всё, что касается
   удобства и масштаба, выносится наружу.

## 6. Открытые вопросы плана

Не блокируют старт, но должны быть закрыты до соответствующего среза.

| Вопрос | Нужен к |
| --- | --- |
| Как устроен поиск по знаниям проекта (`search_project_knowledge`) — полнотекстовый или семантический | S8, влияет на S3 |
| Какой LLM-провайдер и какая стратегия работы с контекстом интервью | S4 |
| Как устроен readiness score — что именно он измеряет | S4 |
| Какова минимальная approval policy: кто утверждает PRD и ADR в проекте из одного человека | S2 |
| Первичный ICP и стартовый workflow (PRD §17 пп. 1–2) | До пилота |
| Первый трекер для интеграции (PRD §17 п. 3) | P4 |

## 7. Принятые риски

- **Нет учёта стоимости LLM в MVP.** Расход агентных запусков ничем не ограничен.
  Приемлемо при одном пользователе, неприемлемо на пилоте с внешними командами —
  закрыть до первого внешнего проекта.
- **Нет инвайтов.** Участники заводятся вручную; пилот с внешней командой потребует
  P3 раньше плана.
- **Один playbook.** Проекты, не похожие на greenfield discovery, в MVP обслуживаются плохо.
- **Нет наблюдаемости.** Диагностика проблем на демонстрации — по логам и вручную.
