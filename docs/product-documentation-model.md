# Intentra - Product Documentation Model

Связано с [Product Brief](product-brief.md), где определены назначение и vision Intentra. Термины ниже определены в глоссариях ([`CONTEXT-MAP.md`](../CONTEXT-MAP.md) и `CONTEXT.md` каждой части системы); здесь они собраны в одну картину и не переопределяются.

## Назначение

Intentra хранит не набор документов, а единую модель знаний проекта. Разговоры, ручной ввод, внешние агенты и проверки проекта её пополняют; Паспорт, контекст для агентов и будущие документы - её представления.

```text
Разговор с Intentra / ручной ввод / внешний агент по MCP / проверка проекта
                              ↓
              Черновики → человек утверждает
                              ↓
                Канонические знания проекта
                              ↓
        Паспорт продукта | Контекст для агентов (MCP) | дальше: документы, план
```

## Канонические знания

Единица знания - **Knowledge Item** ([глоссарий Project Knowledge](../packages/workspace/src/subdomains/knowledge/CONTEXT.md)). У каждой записи есть вид, ключ (`REQ-12`), статус, автор, источник с обоснованием и связи.

### Виды

11 видов; поля каждого и главное поле - в [`docs/notes/knowledge-kinds.md`](notes/knowledge-kinds.md).

| Группа | Виды |
| --- | --- |
| О продукте | Product Overview (один утверждённый на проект), Goal, Persona |
| О поведении | Scenario, Requirement (функциональное или нефункциональное), Business Rule, Integration |
| О языке и рамках | Term, Constraint |
| О решениях | Decision (с отвергнутыми альтернативами), Open Question |

### Связи

`depends on` (держится, пока держится другое), `uses term`, `justified by` (решение - причина), `answers` (закрывает открытый вопрос), `concerns` (открытый вопрос о записи), `conflicts with` (противоречат друг другу). Требование опирается на сценарий, правило - на то, чем управляет; связи и делают из записей модель.

### Жизненный цикл

- **Draft** - записано, но не утверждено. AI (Intentra, Auditor, внешние агенты) записывает только черновики.
- **Approved** - утверждено человеком с ролью Maintainer. Утверждённая запись не правится: её заменяют (**Supersession**) или выводят из обращения (**Retirement**), и старая становится **Obsolete**.
- **Rejected** - отклонено с причиной; повторно такое не записывается.
- **Needs Review** - отметка на всём, что опиралось на изменившуюся запись, пока человек не подтвердит, что оно всё ещё верно.

### Источник

Откуда запись: вручную, внешний агент по MCP, Intentra в разговоре или Intentra в проверке проекта. Кроме ручного ввода, источник всегда несёт обоснование - цитату или пересказ того, на чём запись держится.

## Анализ

То, что делает Intentra аналитиком, а не стенографистом ([глоссарии Project Knowledge и Agents](../packages/workspace/src/subdomains/agents/CONTEXT.md)):

- **Gap** - чего не хватает без всякого суждения: нет обзора продукта, персон или целей; у обязательного требования нет критериев приёмки; у цели нет метрики; у решения нет отвергнутых альтернатив; у сценария нет исполнителя или требований; персона без сценариев; интеграция, на которую ничто не опирается; утверждённая запись без связей. Вычисляется на лету, не хранится, исчезает, когда знание дополнено; черновик уже закрывает пробел.
- **Analysis Run** - проверка, требующая суждения: противоречия, неясности, сомнительные правила. Её выполняет **Auditor** от имени самой Intentra: вручную - по всему проекту, каждую ночь - по тому, что изменилось с прошлой завершённой проверки. Находки записываются черновиками открытых вопросов, связанными с затронутыми записями.
- В разговоре **Intentra** начинает с пробелов и, прежде чем записать новое, сверяет его с утверждённым.

## Паспорт продукта

Читабельное описание продукта для команды, заказчиков и нетехнических участников, только из утверждённых знаний. Восемь глав:

| Глава | Из каких видов |
| --- | --- |
| 1. Обзор | Product Overview |
| 2. Цели | Goal |
| 3. Пользователи | Persona |
| 4. Возможности и сценарии | Scenario, функциональные Requirement |
| 5. Правила и словарь | Business Rule, Term |
| 6. Интеграции | Integration |
| 7. Качества и ограничения | Constraint, нефункциональные Requirement |
| 8. Решения и открытые вопросы | Decision, Open Question |

Черновики и записи на проверке в Паспорт не попадают; он только указывает на них.

## Контекст для AI-агентов

Агент получает не всю базу, а то, что нужно для задачи, и только утверждённое:

- **Project Frame** - что действует для любой задачи: обзор продукта, все ограничения, нефункциональные требования и архитектурные решения. Читается один раз за сессию.
- **Context Pack** - знания вокруг выбранных агентом записей (**Anchors**), собранные по связям без участия модели: на что они опираются (на любую глубину), бизнес-правила, которые нужно соблюсти, что может сломаться, используемые термины, противоречия и открытые вопросы. Каждая запись - со своей ролью; записи на проверке помечены; ближайшие - целиком, остальные - одной строкой.

По MCP агент также видит сводку знаний, пробелы, списки и отдельные записи, а записывает - черновиками. Подробно: [ADR 0002 Agents](../packages/workspace/src/subdomains/agents/docs/adr/0002-agents-run-the-orchestrator-through-agent-toolkit.md) и `MCP_INSTRUCTIONS` в `libs/agent-toolkit`.

## Части системы

- **IAM** - аккаунты и вход.
- **Workspace** - одна часть с одной базой, разделённая на поддомены ([ADR 0001](adr/0001-knowledge-and-agents-are-subdomains-of-workspace.md)):
  - **Tenancy** - пространства, участники, роли, приглашения, проекты, токены доступа;
  - **Project Knowledge** - модель знаний, пробелы, контекст для агентов;
  - **Agents** - собственные агенты Intentra (Intentra, Auditor, Specialists), их версии, разговоры, проверки проекта.

DDD здесь - средство точности, а не ритуал: единый язык живёт в глоссариях, а сами знания проекта несут его собственный язык в виде Terms.

## Дальше

То, что модель уже позволяет, но ещё не построено:

- **Импорт документов** - существующая спецификация разбирается в черновики, и по пришедшему сразу проходит проверка.
- **Планирование** - Feature как вид знания и естественный Anchor контекста, затем Feature → Task с доказательствами выполнения (коммит, PR, тесты):

  ```text
  Goal
    -> Feature
      -> Feature Spec
        -> Task
          -> Commit / PR / Test evidence
  ```

  Задача всегда связана с требованиями и сценариями, поэтому Intentra может ответить человеку, зачем выполняется работа, а агенту - что именно требуется.
- **Документы как представления** - Feature Spec (что должно работать и как это проверить), ADR (почему выбрано решение), пользовательская инструкция (из сценариев и интерфейса), Agent Task Brief (задача с её контекстом и границами).
- **Контекст по тексту задачи** - Anchors, которые Intentra находит сама по описанию задачи.
