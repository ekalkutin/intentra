# Intentra - Product Documentation Model

Связано с [Product Brief](product-brief.md), где определены назначение и vision Intentra.

## Назначение

Intentra хранит не набор разрозненных документов, а единую модель знаний проекта. Интервью с AI, ручное редактирование и импорт становятся её источниками; паспорт продукта, инженерная документация, план и контекст для агентов - её представлениями.

```text
Интервью / ручное редактирование / импорт
                    ↓
        Канонические знания проекта
                    ↓
Паспорт продукта | Документы для агентов | План
```

## Канонические знания

Основные связанные объекты модели:

- термины, факты и источники;
- пользователи, роли, проблемы, цели и метрики;
- возможности продукта и пользовательские сценарии;
- бизнес-правила, требования и ограничения;
- доменные сущности и интеграции;
- решения, риски, допущения и открытые вопросы;
- эпики, features, задачи и доказательства выполнения.

Каждый объект имеет статус, автора, дату, источник и связи с другими объектами. Например, требование связано со сценарием, бизнес-правилом, решением, задачами и тестами. Изменение правила позволяет выявить документы и планы, требующие пересмотра.

## Паспорт продукта

Паспорт - читабельное описание продукта для команды, заказчиков и нетехнических участников. Он не требует знания инженерной терминологии.

1. Обзор: продукт, проблема, аудитория и ценность.
2. Цели и границы: outcomes, метрики успеха, scope и non-goals.
3. Пользователи и участники: персоны, роли, потребности и stakeholders.
4. Возможности и сценарии: что можно сделать в продукте и какой результат ожидается.
5. Правила и словарь: права, политики, ключевые понятия и их определения.
6. Данные и интеграции: важные данные, внешние системы и владение ими.
7. Качества системы: безопасность, приватность, скорость, доступность, аудит и другие ограничения.
8. Решения, изменения, roadmap, риски и открытые вопросы.

Пользовательская инструкция является отдельным представлением: она строится из сценариев и интерфейса и объясняет, как выполнить конкретную задачу в продукте.

## Минимальный DDD-слой

DDD применяется как средство точности, а не как обязательный ритуал.

- **Ubiquitous Language**: единый глоссарий, понятный бизнесу и разработке.
- **Bounded Context**: смысловые границы частей продукта. Для Intentra это могут быть Workspace & Access, Project Knowledge, Interview, Documentation, Planning и Agent Access.
- **Entity**: объект с идентичностью, например Project или Decision.
- **Value Object**: значение без самостоятельной идентичности, например статус или приоритет.
- **Business Rule / Policy**: правило поведения системы.
- **Domain Event**: значимое событие, например утверждение требования или устаревание решения.

## Контекст для AI-агентов

Агент получает компактный контекст под задачу, а не всю базу знаний проекта. Он должен включать ссылки на первоисточники и только актуальные утверждённые сведения.

- **Project Context**: назначение продукта, язык, границы и ограничения.
- **Feature Spec / PRD**: цель, ожидаемое поведение, scope и критерии приёмки.
- **ADR**: почему выбрано важное решение и какие альтернативы отвергнуты.
- **Domain Model** и **API / Integration Contract**: правила предметной области и контракты границ.
- **Technical Design**: способ реализации feature в существующей архитектуре.
- **Acceptance Criteria / Test Scenarios**: как доказать корректность результата.
- **Agent Task Brief** и **Constraints**: текущая работа, релевантный контекст, границы изменений и стандарты качества.

ADR отвечает на вопрос «почему», spec - «что должно работать», technical design - «как реализовать», а task - «какой следующий проверяемый шаг выполнить».

## Планирование

План строится от результата к реализуемым шагам:

```text
Vision
  -> Objective / Outcome
    -> Epic
      -> Feature
        -> Feature Spec
          -> User Story / Vertical Slice
            -> Task
              -> Commit / PR / Test evidence
```

Objective задаёт бизнес-результат и метрику. Epic объединяет крупную проверяемую ставку. Feature описывает пользовательскую возможность. Spec фиксирует контракт поведения. Задача остаётся небольшим проверяемым действием с критериями приёмки и зависимостями.

Задачи всегда связываются со спецификацией и требованием. Благодаря этому Intentra может ответить человеку, зачем выполняется работа, а AI-агенту - что именно требуется реализовать.

- [mattpocock/skills](https://github.com/mattpocock/skills) - практики интервью (`grill-me`), общего языка, domain modelling, ADR, спецификаций и декомпозиции на задачи.
