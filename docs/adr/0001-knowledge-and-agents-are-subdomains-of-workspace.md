# Project Knowledge and Agents are subdomains of the Workspace context

Project Knowledge and Agents were planned as contexts of their own next to Workspace. Every action in both starts by asking Workspace who the caller is in the Workspace and what their Role or Project Role allows, and everything in both goes when its Workspace, Project or Member goes. Across a context boundary that means a call into Workspace on every request and events to carry deletions, with the risk of leftovers when a delivery fails. So Workspace is one bounded context with one database and one transaction boundary, split into three subdomains: Tenancy (Workspaces, Members, Roles, Invitations, Projects, Project Roles, Personal Access Tokens), Project Knowledge and Agents; every subdomain checks rights through Tenancy's `AccessResolver` and `AccessPolicyService` (who is who in the Workspace and what their Role or Project Role allows), adding its own rules in a policy of its own on top of them, and deleting a Workspace, Project or Member removes what depends on it in the same transaction. Each subdomain keeps its own glossary, so the languages do not mix. The agents' runtime (Mastra, tools, LLM providers) stays outside, in `libs/agent-toolkit`, and reaches the context only through its published API.

## Considered Options

- **Three contexts, Knowledge and Agents downstream of Workspace** (how x-lance's Assistant calls Organization's `access.resolve`). Rejected: both need Workspace's answer on every request and both must follow Workspace deletions, so the boundary would cost a call per request and a set of events without buying independence; they share the process and the database anyway.
- **Only Knowledge inside Workspace, Agents separate.** Rejected: Agents stores only Workspace-owned data (Agent Settings, Skills, Model Profiles, Provider Key, Conversations) with the same rights and deletion ties, so it would have to solve the same problems a second way. The part that is truly separate, the runtime, already lives in `libs/agent-toolkit`.

## Consequences

- One package, laid out like x-lance's Organization context: `packages/workspace/src/subdomains/{tenancy,knowledge,agents}`, each with its own `domain`, `application` and `infrastructure`. The context level holds only the wiring: the Nest module and the published `WorkspaceApi`, which gathers every subdomain's sub-API. Access stays in Tenancy: lifting it to the context level would make it import Tenancy's entities while Tenancy's domain services use it, a cycle. The Workspace aggregate itself lives in Tenancy, as x-lance's Tenant lives in its `tenancy` subdomain.
- A subdomain imports another only through its `index.ts`, never its layers directly.
- Dependencies point one way: Knowledge and Agents depend on Tenancy, Agents on Knowledge, never the reverse. Tenancy declares one port, `Cleanup` (`afterWorkspaceDeleted`, `afterProjectDeleted`, `afterMemberRemoved`). A Tenancy service first deletes the Workspace or Project, or saves the Member as Removed, then calls it in the same transaction, and it removes everything that lies under it, Tenancy's own data included. Its one implementation, `CleanupAdapter`, lives at the context level, next to the module, and is the only place that knows what lies under what in every subdomain. In-process domain events were rejected for this: an event reports what happened and is not a way to keep data consistent (the same rule as x-lance's ADR 0016).
- The Workspace package grows; a subdomain that one day needs independence (its own store, its own deployment) can be split out along its boundary.
- IAM stays a separate context.
