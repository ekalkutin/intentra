# База данных на bounded context

Дата: 2026-09-22. Статус: принято.

## Контекст

Intentra — модульный монолит (PRD §9): один процесс, изолированные доменные модули.
Отсюда не следует ответ на вопрос, где живут их данные. Рассматривались одна база со
схемой Postgres на контекст и отдельная база на каждый контекст.

## Решение

У каждого bounded context своя база данных. Контекст — кандидат на выделение в
отдельный сервис при масштабировании, и база переезжает вместе с ним.

Следствия для модели: внешних ключей и джойнов между контекстами не существует, ссылки
на чужие сущности хранятся идентификаторами, общих транзакций нет.

## Considered Options

- **Одна база, схема на контекст.** Отвергнуто: позволяет общую транзакцию, а значит
  рано или поздно она появится там, где её быть не должно, и вынос контекста в сервис
  перестанет быть переносом схемы.
- **Одна база, одна схема.** Отвергнуто сразу: границы контекстов держатся правилами
  линтера в коде, а в SQL не держались бы ничем.

## Consequences

- Регистрация `Account` и создание `Workspace` — два разных действия пользователя
  и две транзакции в двух базах. Компенсация не нужна именно потому, что это разные
  действия; если бы они были одним, понадобилась бы сага.
- Локальная разработка — несколько строк подключения и несколько баз в одном инстансе
  Postgres.
- Движок исполнения агентов держит свою базу на тех же правах
  ([ADR 0005](./0005-mastra-owns-the-conversation.md)).
