# Agents: open questions

Deferred on purpose. Glossary: `packages/workspace/src/subdomains/agents/CONTEXT.md`.

- **Plans and usage on Intentra's models.** Decided on 2026-10-01: the MVP is sponsored and tried by a small group, so there is one implicit plan, Free (BYOK): a Provider Key is required and Intentra never pays for a Workspace's model calls. No Plan in the model yet, no usage limits. With billing and usage metering comes a Plan on each Workspace (all existing ones get Free), and a paid Start plan where Agents may run on Intentra's key, so a Provider Key becomes optional there.
- **More LLM providers.** For now a Provider Key can only be an OpenRouter key. Later: direct keys to Anthropic, OpenAI and others. Options discussed on 2026-09-29: one key per Workspace, one key per provider (a Model Profile names its provider; mixing providers is allowed), or any number of keys with a Model Profile naming its key (for splitting costs). One key per provider was the preferred option.
- **Conversations outside a Project.** For the MVP a conversation always lives in a Project. Later, two growth paths, and the model must not block them:
  - *Idea → Project ("wow" start):* a conversation starts in the Workspace with no Project, the Orchestrator asks what is being built, offers to create the Project, creates it after the Member confirms, and the conversation is attached to it for good (once, one way). Right after, the Agent records what it already learned. Open: only the Owner may create a Project today, so what happens when a Contributor starts such a conversation; and what happens to abandoned conversations that never got a Project.
  - *Cross-project questions:* a Workspace-level conversation reads across Projects ("which of our projects integrate with Stripe?") and writes nothing. Open: filtering by per-Project access once it exists.
  - What to lay down now: a conversation always records its Workspace, and its Project separately; Agents and tools take the scope (Workspace, Project) from the request context, never assume a Project is there.
- **Built-in Model Profiles.** Decided on 2026-09-30: the first slice of Agents runs the Orchestrator on one model from env (`OPENROUTER_API_KEY`, `AGENT_MODEL`), with no Model Profiles. We must come to Intentra's built-in Model Profiles ("Fast", "Smart", …) from the glossary, which Intentra assigns to its Agents itself, before (or together with) Agent Settings and the Workspace's own Model Profiles on a Provider Key. Superseded on 2026-10-01 by Agents ADR 0003: instructions and built-in Model Profiles become data a Platform Admin edits and publishes.
- **Orchestrator instructions as Skills.** Decided on 2026-09-30: the first slice carries the Orchestrator's instructions over from the UI prototype as they are (a function in code, the text depending on the Project Role). Later, most likely with Skills: keep short instructions and move the interviewing know-how into Intentra's own Skill (markdown via `createSkill`, read on demand), or at least keep the text in a markdown file; pick whichever works better on live Conversations. Superseded on 2026-10-01 by Agents ADR 0003: instructions and built-in Model Profiles become data a Platform Admin edits and publishes.
- **One answer at a time across several API instances.** Decided on 2026-09-30: while the Orchestrator answers in a Conversation, another message to it is refused with 409; the mark "an answer is in progress" lives in the API process's memory, which holds while the API runs as one instance. With several instances, move it to MongoDB (a lock with an expiry).
- **Stopping an answer.** An answer runs to the end on the server even if the client goes away (limited by steps and a timeout). A "stop" button comes with the UI if people need it.
- **Memory about the Member.** Decided on 2026-09-30: every Conversation starts clean. Mastra's working memory scoped to the Member (role, style, preferences) is a likely next feature, but needs a place where the Member sees and edits what is remembered.
- **Live evaluations of the Orchestrator.** Tests use a scripted stand-in model only. Checking the quality of the interview on a real model (evals) is a separate, deliberate piece of work.
- **Importing documents.** A message is limited to about 20 000 characters, so an existing specification cannot be pasted whole. Importing documents is the third source of knowledge in the product brief and should be its own feature, not "paste it into the chat".
- **Deleting while an answer runs.** A Member's own edit or deletion waits for the answer (409), but deleting a Project or Workspace, or a Member leaving, does not: the running answer may save its last messages after their thread is gone, leaving messages nobody can reach. Not data loss; clean them up if it ever matters.
